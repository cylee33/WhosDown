## Goal

When a Match is Full, Players can line up. When a spot opens, the first in line gets 10 minutes to claim it, and then it passes to the next.

## Data

| ID | Read / write | Path and fields |
|---|---|---|
| W6 (waitlist) | write (transaction) | `rsvps/{me}`: `status: "waitlisted"`, `waitlistedAt` (server time); `waitlistCount += 1` |
| Offer | write (in the same transaction as the leave, or the expiry pass) | First waitlisted RSVP (oldest `waitlistedAt`, no live offer): `spotOfferExpiresAt = now + 10 min`; notification `spotOpen` |
| W9 claim | write (transaction) | `rsvps/{me}`: `status: "approved"`, `spotOfferExpiresAt: null`; `joinedCount += 1`, `waitlistCount −= 1` |
| Pass | write (transaction) | Expired or declined offer: clear it on that RSVP and offer the next in line |
| R3 | read | `rsvps` where `status == "waitlisted"` ordered by `waitlistedAt` → position |

**Security rules this feature needs:**

- Join waitlist only when the Match is Full and `waitlistEnabled`.
- Claim only with a live offer (`spotOfferExpiresAt > request.time`) and a free spot.
- Setting `spotOfferExpiresAt` on **another** Player's RSVP is allowed only when (a) the writer's own RSVP goes from approved to left in the same write, (b) the current offer has expired, or (c) the writer is the Host raising the limit (1.18). It must be the first in line, and the time must be `request.time + 10 min`.

## Rules and edge cases

1. Order is by `waitlistedAt`. Position is computed, not stored.
2. Only one live offer per open spot. Two spots open means the first two in line get offers.
3. **Claim** inside 10 minutes moves the Player to approved and takes the spot.
4. **Stay on waitlist** gives up this offer: the offer passes to the next Player. See Open questions for where this Player goes.
5. **Expiry:** when anyone opens the Match (or the Host's dashboard) and finds an expired offer, the app passes it on in one transaction (D24). With no one left in line, the spot is just open.
6. **Expired offer, offered Player:** see Open questions.
7. **Approval-required Matches:** see Open questions.
8. Full with no waitlist: the button says "Full" (disabled), plus "Find similar Matches" (D24).
9. Raising the player limit (1.18) offers new spots to the waitlist the same way.
10. Pending requests can't be approved while Full (D24, 1.15). When a spot opens, the waitlist gets it, not the pending requests.
11. The Match starting ends the waitlist: no new offers after the start.

## Open questions

1. **After an offer expires or the Player taps "Stay on waitlist":** _Suggested:_ they stay on the waitlist but move to the back of the line.
2. **Waitlist on Approval-required Matches:** what happens when a waitlisted Player claims a spot? _Suggested:_ joining the waitlist of an Approval-required Match sends a Join request first. The Host approves them **onto the waitlist**, so a claimed spot goes straight to approved. The alternative, the claim becoming a new Join request, could leave spots unfilled.
