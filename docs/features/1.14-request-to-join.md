## Goal

On a Match whose Join type is **Approval required**, a Player sends a Join request with an optional note to the Host. They see it as **Pending**, and the screen changes live to **Approved** or **Declined** (with the Host's message) when the Host answers.

## Data

| ID | Read / write | Path and fields |
|---|---|---|
| R2 | read (listener) | `matches/{matchId}`: `startTime`, `venueName`, `priceCents`, `joinType`, `hostId`, `hostName`, `joinedCount`, `playerLimit`, `status` |
| R4 | read (listener) | `matches/{matchId}/rsvps/{me}`: `status`, `hostResponse` |
| W6 | write (transaction) | Create or overwrite `matches/{matchId}/rsvps/{me}` with `userId`, `displayName`, `skillLevel` (my level for this Match's sport), `status: "pending"`, `isHost: false`, `noteToHost` (or null), `requestedAt` (server time), `respondedAt: null`, `hostResponse: null`, `checkedIn: false`, `attended: null`. In the same transaction, increment `matches/{matchId}.pendingCount` by 1 |

Approving and declining (W7) belong to 1.15. Cancelling (W8) belongs to 1.16. This feature only **listens** for the result.

**Security rules this feature needs** (`firebase/firestore.rules`, with emulator tests):

- A Player can create or update only `rsvps/{their own uid}`, and can't overwrite one whose status is `declined`.
- On an Approval-required Match, a Player can set their own status only to `pending`, never to `approved`.
- The write is allowed only if `pendingCount` goes up by exactly 1 in the same write (`getAfter`), the Match `status == "scheduled"`, `request.time < startTime`, and the Player isn't the Host.
- `noteToHost` is a string of at most 300 characters, or null.

## Rules and edge cases

1. The button on H09 shows **"Request to join"** when the Match is Approval required, not Full, scheduled, not started, and the Player has no active RSVP (none, or `left`).
2. If the Match is **Full**, show "Full · Join waitlist" instead (1.17), or "Full" if there's no waitlist (D24).
3. The **Host** never sees a join button on their own Match.
4. A **Guest** tapping the button gets the H34 sheet to create an account (D27). Nothing is written.
5. With an RSVP already, the status card replaces the button: pending shows H13, approved shows H14, declined shows H35, waitlisted shows H15 (1.17).
6. **Pending does not take a spot.** `joinedCount` doesn't change; only `pendingCount` goes up.
7. **No double counting.** If the transaction finds an existing `pending` RSVP (double tap, two devices), it changes nothing.
8. **Request again after cancelling:** allowed. The `left` RSVP is overwritten with a new pending one.
9. **No request after a decline.** A decline is final for that Match; H35 shows no request button, only "Find similar All-Level Matches" and "Back to Discover". Security rules refuse overwriting a `declined` RSVP.
10. The note is optional. Trim spaces; an empty note is saved as null.
11. The screen follows R4 live. When the Host answers, it switches to H14 or H35 without a refresh.
12. While the Match is Full, the Host can't approve pending requests (D24, enforced in 1.15). The Player keeps seeing Pending.
13. If the Match is cancelled while the request is pending, show the cancelled state from 1.18, not Pending.
14. "Find similar All-Level Matches" on H35 opens the Discover list filtered to this Match's sport and All Levels (uses 1.6 and 1.7).
15. **Price line on H12:** a free Match says "You won't be charged" / "This Match is free." A paid Match shows the price, display only.
16. **No response-time line in V1.** Hide "Jamie usually responds within 20 minutes" on H12 and H13; it needs `avgResponseMinutes`, a V2 stat (2.7).
17. **Requests close at the Match's start time.** After that, no join button shows.
18. **Note to Host:** at most 300 characters; the field shows a counter and stops input at 300.
